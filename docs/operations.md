# 运行维护

## 每日采集

默认每天 UTC 01:17（北京时间 09:17）运行。调度文件必须位于默认分支。GitHub 在繁忙时可能延迟或丢弃调度任务；公开仓库长期无活动时，定时工作流也可能停用。遇到停用，在 Actions 页面重新启用并手动运行一次，不把本地手动验证视为定时触发成功。

每次任务输出来源状态、成功数量和来源验收表。网站右上角显示数据快照时间，最近采集成功时间见 `/data/sources.json`；`/data/health.json` 可用于外部监测。故障通知使用 GitHub Actions 原有通知机制。

## 阅读界面验收

发布前检查 PC 的横向多列和手机的单列滑动。每列独立上下滚动，顶部公司导航能定位到对应列。聚焦看板后，左右方向键也能切换列。手机展开搜索后仍能关闭，并且不会增加整页横向溢出。文章详情和 About 保持正常纵向阅读。

搜索、当前公司列和已加载批次需要在刷新及浏览器前进后退后恢复。可用 `?q=Agent&company=dewu&page=2` 检查直达链接；`page=2` 表示当前列已加载两批，共最多 40 篇文章。文章始终最新优先，旧链接中的 `sort=oldest` 会被清理。列表不显示数量，触底时自动追加一批。确认追加后不会在没有继续滚动时连续加载所有文章。

核对 ATOM/RSS 小窗中的两个全站链接与复制结果，检查复制失败提示、Esc、点击外部关闭和焦点恢复。验证深浅色切换及刷新后的保存、GitHub 图标链接、文章标题直达发布网站，以及文章详情的项目子路径直达。确认界面没有更多菜单、排序控件、公司订阅入口、来源目录、列表数量和底部切换控件；更新时间位于右上角。检查链接悬浮动画和键盘焦点。截图与人工体验只是界面证据，发布成功仍以构建、部署及线上检查结果为准。

## 数据分支

数据分支仅包含 `snapshot/manifest.json`、`snapshot/articles/` 和 `snapshot/sources/`。清单记录 schema 版本、数量及 SHA-256。每次从完整快照恢复，不依赖临时缓存或过期 Artifact。

采集先写工作副本，经数据校验、构建及浏览器验收后，使用普通 Git 提交推送。写入互斥且禁止强推。数据提交不会触发 `main` 分支工作流。

本地数据命令使用快照目录旁的 `.lock` 文件互斥。异常退出后，先查看锁内的进程号并确认进程已结束，再删除该锁文件；不要删除快照目录。每日采集使用 `--daily`，避免运行耗时造成 24 小时轮询间隔逐日漂移，同时保留 HTTP 条件请求。

损坏或无法识别的版本会立即失败，不自动重建空库。需要迁移时先实现显式迁移并保留旧快照提交。

本批国内迁移使用 `pnpm data:migrate-domestic`。它先验证旧快照完整性，再按当前国内注册表删除海外文章和来源状态，并将国内账号文章直接纳入索引。重复执行不会重建数据。恢复旧版含海外来源的快照后，必须先执行迁移再校验和发布。

该命令也处理 `packages/source-registry/replacements.ts` 明确登记的来源替换。维护者明确移除且没有替代的来源登记在 `sourceWithdrawals`，同时移除公司栏目；恢复旧快照时会再次清理这些来源的状态与独占文章。标记为 `referenceOnly` 的参考入口只删除空状态；若发现关联文章则报错。此类清理允许保留源维持暂停状态，不要求重新启用历史源。只有替代来源已经核验、启用并存在成功采集记录及已发布文章，才移除旧源位置与状态；仅剩旧源位置的文章退出快照，仍有其他有效位置的文章保留原 ID。缺少替代证据时迁移失败，旧快照不会被覆盖。恢复替换前的快照后，发布流程会重新执行同一迁移；恢复操作不会重新上线已移除的旧源。

每家公司在注册表中恰好保留一个来源。更换来源时，先用新源配置在隔离快照完成真实采集，将成功状态与文章合入待迁移的原快照，再移除旧源并执行迁移。准备好代码与数据提交后，可用 Git 原子推送同时更新 `main` 和 `data`，避免发布过程读到缺少替代证据的中间快照。若远端数据已经变化，停止发布，基于最新快照重新准备，禁止强推覆盖。恢复更早且缺少新来源的快照时，也需要先在临时配置中补齐替代采集，或改用已经完成替换的合法快照。

## 恢复数据

1. 停止新的手动采集，等待正在执行的发布完成。
2. 检查 `data` 分支历史，找到通过校验的快照提交。
3. 在数据分支使用 `git revert` 撤销损坏提交，或从指定提交恢复 `snapshot/` 并创建新提交；不用强推覆盖历史。
4. 运行数据校验，再手动执行关闭 `collect` 的发布。

网站部署失败时，已经保存的合法数据仍可重用。构建失败或全部来源失败时，已部署的网站保持上一个版本。

## 来源故障

采集成功与近期活跃分别核验。来源 JSON 中的 `latestPublishedAt` 表示已公开收录文章的最近发布日期，不用采集时间替代。来源核验和实测结果还可查看仓库内的[来源验收表](source-acceptance.md)。尚无可靠替代的过时渠道以 `suspended` 暂停新增并保留历史；已完成替换的旧渠道从注册表与快照移除。健康快照的成功和失败数量只统计启用渠道。

身份核验与采集成功独立。403、robots 禁止、验证码、入口不可用或解析不到文章均不能标记为接入成功。改变入口或适配器需要重新执行该来源的真实采集。

单来源诊断可运行 `pnpm ingest --force --source=来源ID`。身份待确认的入口只检测可达性，绝不自动升级认证。未获取到文章的来源不会更新最近采集成功时间。

## 发布安全

生产构建和订阅导出默认使用 `https://liuminxin45.github.io/ai-engineering-radar`。自定义部署用 `SITE_URL` 设置公开站点根地址，用 `BASE_PATH` 设置路径前缀；根路径部署显式设为空。页面元数据与订阅使用同一地址解析逻辑，localhost 或回环地址会在构建、导出前报错。开发服务器地址与公开订阅地址分别配置。

PR 工作流使用固定夹具和只读权限；公开部署工作流仅运行本仓库默认分支代码。构建产物必须通过公开内容检查，禁止发布测试夹具、私人路径和凭据。首批不使用模型服务，不需要模型密钥。

HTTP 采集器限制公开 HTTP(S) 地址、来源域名和重定向，拒绝私有地址；不接受用户传入临时抓取 URL。遵守 robots 和访问限制，网络响应只在内存中解析，不提交原始页面。
